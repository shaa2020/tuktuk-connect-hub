## Architecture rules
- Subdirectories have their own AGENTS.md (src/lib) — read it before changing files there.
- App branding uses shared BrandMark/BrandLockup components backed by CDN asset pointers; install icons use real versioned public files to prevent stale cached artwork.
- Business data is scoped by `workspace_id`; access is enforced by RLS helpers (`is_member`, `has_ws_role`, `can_view_conversation`) — UI checks in `src/lib/domain.ts` only mirror them.
- CRUD runs from the browser client under RLS; multi-row or privileged operations are SECURITY DEFINER RPCs that check the caller's role first — keeps logic atomic and server-enforced.
- The app may only insert messages with status `logged`; channel delivery statuses come solely from server-side webhook handlers — prevents fake delivery states.
- Protected pages live under `src/routes/_authenticated/` (client-only gate, redirect to `/auth`).
- Sample data is flagged `is_demo` and labelled "[SAMPLE]" — never mixed with real records.
- tsconfig relaxes exactOptionalPropertyTypes / noPropertyAccessFromIndexSignature / noImplicitReturns — generated DB types are incompatible with them.
- AI calls go through `src/lib/ai.functions.ts` (requireSupabaseAuth, RLS-scoped reads) → `ai-gateway.server.ts` (streamed Responses API); output is a labelled suggestion, never auto-sent — except the AI Operator.
- Webhooks start the AI Operator via the kick_ai_operator RPC (pg_net, 120s timeout, background-sync operatorOnly), never inline — inline runs were cut off on caller disconnect.
- Outbound sends share src/lib/outbound.server.ts so team and operator replies use the same channel routing.
- Automations are evaluated in a DB trigger on conversation insert and logged to `automation_runs`.
- Third-party credentials live encrypted (AES-GCM, server key) in `workspace_secrets`, which has no client grants; only server functions read them after `has_ws_role` admin checks, and the UI only ever sees masked hints — secrets are never returned to browsers.
- Meta channels ingest via `/api/public/webhooks/meta/$workspaceId` (verify token + X-Hub-Signature-256) and send via `sendChannelMessage`; only these server paths set sent/delivered/read statuses.
- Email channel uses the linked Gmail connector server-side (email-channel.server.ts); inbox polls syncEmailNow while open since Gmail push needs Pub/Sub — keeps setup credential-free.
- Invite-only access: public signup disabled (auth config); /auth is sign-in + reset only; new accounts are created server-side by redeemInvitation (src/lib/invite.functions.ts) when a valid invitation token is opened, then the invitee sets their password via a reset email.
- Channels are multi-account: one channel_connections row per account (unique workspace+channel+account_id); conversations.connection_id records the receiving account; Meta tokens are stored per connection as `<channel>_token:<connectionId>` — so replies always leave from the account the guest contacted.
- Extra Gmail inboxes use IMAP/SMTP over node:tls with a Gmail App Password stored encrypted as gmail_pass:<connectionId>; rows have config.mode='imap' — the Lovable Gmail connector only supports one account.
- WhatsApp primary number uses the Lovable WhatsApp connector (config.mode='connector'): sends via connector gateway, receives at /api/public/whatsapp/webhook into the durable whatsapp_webhook_events inbox with bounded retry — no Meta tokens stored.
- MFA: TOTP is mandatory; MfaGate (src/components/mfa-gate.tsx) fails closed on lookup errors and forces enroll/verify; a phone can only be removed while another verified one exists; lost phones are reset by an admin via resetMemberMfa (audited) - no path leaves an account without MFA.
- Background sync: pg_cron every 5 min POSTs /api/public/hooks/background-sync with a random token read from internal_job_tokens (service_role only) — Gmail push and website webhooks aren't available, and the token never leaves the server/DB.
- Connect Account sheet (src/components/connect-account.tsx) derives card states only from real channel_connections rows via src/lib/connect-providers.ts (tested) and hands off to /integrations?connect=<channel> — one setup path per provider, no fake states.
- Booking overlaps (same guide or tuk tuk, confirmed bookings) are blocked in the DB trigger booking_conflict_guard with a per-day advisory lock; a busy default guide is skipped instead of failing — client findConflicts is only a preview.
- Ticket boarding uses the check_in_ticket RPC (members only, row-locked) so a second scan reports "already checked in".
- PayPal finance (src/lib/paypal.server.ts): admin saves Live Client ID/Secret encrypted; background sync (~hourly, 3 days) and "Check now" (31 days) pull the Reporting API into paypal_transactions (manager/admin read-only RLS); matching rules are pure and tested (paypal-match.ts) — only completed PayPal money sets payment_status, never for website-synced bookings.
- Operator-owned integrations (Lovable Gmail/WhatsApp connectors, tuktuk24lisbon.com API) act only for workspaces with platform_connectors=true, checked by assertPlatformConnectors (src/lib/tenancy.server.ts, fails closed) before any network call — prevents new tenants reaching the operator's mailbox, bookings or WhatsApp number.
- Browsers may update only ordinary workspace columns (column-level GRANT, migration 0019); plan, plan_limits, owner, suspension and platform_connectors change only via service role or platform_* RPCs — tenants can't self-upgrade.
- Child rows may only reference same-workspace parents/members (enforce_same_workspace / enforce_member_ref triggers) — blocks cross-tenant linking even from server code.
- Suspension: is_member/has_ws_role/can_view_conversation return false for suspended workspaces; background jobs skip them; inbound webhooks still store customer messages.
- Plans & limits live in the plans table (+ workspaces.plan_limits overrides); hard limits are DB triggers/assert_entitlement, metered actions use consume_usage (service role only); conversations are a soft limit so customer messages are never dropped. Every AI call is metered in generate() (ai-provider.server.ts).
- New tenants are created only by the create_workspace RPC (verified email, max 3 owned) — the caller becomes owner + admin, plan 'free', platform_connectors false.
- Database policy tests: `npm run test:db` starts a throwaway local Postgres, applies every migration (0019+ twice for idempotency) and runs db-tests/ — add a test there for any RLS/RPC change.
- Public, unauthenticated endpoints are throttled with check_rate_limit (src/lib/rate-limit.server.ts): credential-like lookups fail closed, provider webhooks fail open (providers retry on 429) — never drop customer messages because the limiter is down.
- Tenant-supplied outbound URLs (custom AI provider) must pass unsafeUrlReason (src/lib/url-safety.ts) on save and at call time — SSRF guard.
- Background sync fans out: the scheduler tick ({} body) runs global tasks and calls trigger_background_sync_fanout (one pg_net request per non-suspended workspace, body {workspace}); per-workspace work lives in background-jobs.server.ts; falls back to serial processing if the RPC is missing.
- Social publishing (social-publish.ts pure/tested + social-publish.server.ts): due posts are claimed scheduled→publishing, published to connected Facebook Pages / Instagram via saved Page/IG tokens, per-target results stored, max 3 attempts; browsers can only save draft/scheduled (trigger + column grants) — no faked publish states.
- White-label: product name is APP_NAME (src/lib/brand.ts) on public pages; inside the app use the workspace name. TukTuk24-specific copy/defaults stay only behind platformConnectors (operator) — e.g. tickets keep the operator domain/wording, other businesses get their own name + app_config.app_base_url.
- Industry modules: modulesFor(industry, platformConnectors) in use-workspace.tsx decides optional tools (tours = tour calendar, dispatch, quotes); NAV items carry `module` and are hidden when off. Industry is editable in Settings.
- Telegram channel: each business connects its own @BotFather token (telegram.server.ts; encrypted telegram_token:<connId>); webhook /api/public/webhooks/telegram/$connectionId is authenticated by a per-connection secret (X-Telegram-Bot-Api-Secret-Token); only private chats are imported (parseUpdate, tested).
- Website live chat: public/chat-widget.js (ASCII-only, no cookies) talks to /api/public/chat/$key (public widget key wk_…, visitor id v_<uuid> kept in the visitor's localStorage acts as their session); CORS limited to the business's allowed origins when set; per-IP and per-key rate limits; team replies are stored outbound and fetched by widget polling.
- SaaS billing = Stripe (stripe.ts pure/tested, stripe.server.ts, /api/public/webhooks/stripe): checkout/portal only for admins; webhook verified (Stripe-Signature, 5-min tolerance), deduped via billing_events (claim released on failure so Stripe retries), sets workspaces.plan from the subscription (paid while active/trialing/past_due, else free) and never touches plan 'internal'. Off until STRIPE_SECRET_KEY + STRIPE_WEBHOOK_SECRET + plans.stripe_price_* are set.
- Staff scheduling (migration 0025, /schedule): managers write shifts (RLS), DB blocks overlapping shifts per person and non-member assignees, employees request time off / offer swaps of their own shifts only; managers decide via decide_time_off / decide_shift_swap (audited, notifies); attendance only via clock_in/clock_out RPCs (server time). Not legal timekeeping.
- CRM: contact import goes through import_contacts (admins/managers, ≤2,000 rows/call, skips email/phone duplicates, audited); duplicates via find_duplicate_contacts + existing merge_contacts; custom fields are defined per workspace (contact_field_definitions, admin) and validated by a trigger on contacts.custom_fields. CSV parsing is pure/tested in src/lib/csv.ts.
- Automation workflows (0027): DB triggers enqueue automation_events (unique workflow+idempotency key, delay, over-limit → skipped) and never block the business write; automation.server.ts (background job) claims events, checks conditions, runs actions, retries ×3 only when nothing succeeded. Trigger functions shared across tables must use nested IFs — PL/pgSQL doesn't short-circuit AND.
- Data lifecycle (0028): owner-only transfer_workspace_ownership / request_workspace_deletion (type name, 30-day grace, cancellable); purge_due_workspaces + apply_message_retention run from the background job (service role) and never touch the operator workspace; full JSON export via exportWorkspaceData uses the admin's RLS client and excludes secrets. Triggers that write rows on DELETE must skip when the parent workspace is gone (cascade-safe).
- AI approval mode: when the AI Operator's "reply" permission is off, its replies go to ai_reply_drafts (no client inserts) and are sent only when a person taps Approve & send in the inbox (normal sendChannelMessage path, authored by that person). Auto-classification (ai_settings.auto_classify) labels intent/sentiment/summary in the background; it is a suggestion and metered.
- Platform support access is consent-based: a business admin grants 1–72 h (grant_support_access); platform admins then get a read-only, audited snapshot (support_workspace_snapshot) — there is no impersonation login. Revenue/health RPCs return counts and provider error strings only.
- MFA recovery codes: 10 one-time codes, only salted SHA-256 hashes stored (mfa_recovery_codes, service role only); generating requires aal2; redeeming (rate-limited, audited) deletes the user's factors and signs them out so they enrol a new phone — MfaGate still forces MFA before any data access.
- Theme: light/dark/auto via the "dark" class on <html> (src/lib/theme.ts, THEME_BOOT inline script prevents a light flash); all colours are tokens in styles.css (.dark overrides) — never hard-code colours.
- Global search (Ctrl/⌘K, command-palette.tsx) queries contacts, conversations and bookings through the RLS client, scoped to the current workspace; results only ever show what the person may already see.
- Attachments (0032): private Storage bucket `attachments`, paths `<workspace>/<conversation>/<uuid>-<name>`; storage + message_attachments policies use attachment_path_allowed (can the caller see that conversation, in that workspace). Browsers upload directly under RLS; sending to customers goes through sendAttachment → attachments.server.ts (signed URL, per-channel media API); inbound Telegram/Meta media is downloaded server-side (≤15 MB) into the same bucket. The Lovable WhatsApp connector's inbound media is not downloaded (no documented media endpoint) — placeholder text stays.
- Services & online booking (0033): services hold weekly hours, capacity, price and mode (slot | day). Public page /book/$slug calls server functions in booking-page.functions.ts (rate-limited, honeypot) → service_role-only RPCs public_booking_page / public_create_booking, which re-check capacity under an advisory lock. Bookings arrive tentative unless booking_auto_confirm is on, and managers are notified. Availability comes only from service_availability (workspace timezone, lead time, advance days).
- Inbox speed tools (0034): shortcuts are a pure keymap (src/lib/inbox-keys.ts, tested) and never fire while typing. Snooze hides a conversation from working views until snoozed_until (time-based filter, no job); any inbound message clears it in a DB trigger. Bulk actions are plain RLS updates, so rows a person may not change are skipped and reported. Viewing/typing presence uses private Realtime channels `conv:<id>`, authorised by realtime_conv_allowed (can_view_conversation_id).
- AI knowledge documents (0035): uploads (PDF via lazily loaded pdf.js — browser only, folded out of the SSR build; .docx via a built-in zip reader; text/MD/CSV/HTML) are turned into text in the browser and saved as knowledge_documents (≤200k chars). A trigger keeps knowledge_chunks in sync; both AI paths call loadKnowledge (knowledge.server.ts) → knowledge_context RPC, which sends small knowledge bases whole and otherwise only the passages matching the conversation (terms from queryTerms, tested). Scanned PDFs have no text — no OCR.
- Multi-business people: with 2+ memberships and no valid remembered choice on this device, the app shows a Choose-a-business screen (after MFA) instead of opening the first one; the top bar shows the current business name. Every per-person list that spans businesses (e.g. notifications) must also filter by the current workspace_id — RLS allows all of the person's businesses.
